# AI エージェントのためのコードレビュー & リファクタリング指南書

このドキュメントは、AI エージェント（または人間のエンジニア）が既存プロジェクトのレビュー・ブラッシュアップ・リファクタリングを行う際の思考プロセス・手順・手法をまとめたものです。FlonCSS v3.0.0 のリファクタリングセッションで実際に使われたプロセスを一般化しており、**利用シーンはこのリポジトリに限りません**。各原則には、このセッションで実際に起きた事例を「実例」として添えています。

対象読者: 「このプロジェクトをレビューして、より良くしてください」という開放的な依頼を受けた AI エージェント。

---

## 0. 大原則

すべての作業の土台になる 5 つの原則。迷ったらここに戻ること。

1. **推測しない。実行して確かめる。** コードを読んで「正しそう」と判断するのではなく、ビルドし、出力を検査し、可能なら実行環境（ブラウザ等）で観測する。
2. **ドキュメントは「約束」、コードは「現実」。バグはその差分に棲む。** README が宣言している仕様はすべて検証対象のリストである。
3. **変更は分類してから行う。** すべての変更を「バグ修正（安全）/ 破壊的変更（バージョニングと移行ガイドが必要）/ ドキュメント修正」のどれかに分類し、扱いを変える。
4. **自分の変更が最大の疑うべき対象。** 変更を加えたら、変更前と同じ厳しさで自分の diff をレビューする。
5. **判断の優先順位は、正確性 > 互換性 > 単純さ > 効率 > スタイル。** 上位を犠牲にして下位を改善しない。

## 1. フェーズ 0: 全体把握 — 読む前に構造をつかむ

コードを 1 行も読む前に、プロジェクトが「何であると主張しているか」を把握する。

### 手順

1. **メタデータから読む**: `package.json`（または相当ファイル）の `exports` / `files` / `scripts` / `bin` / 依存関係。これはプロジェクトの「公開インターフェース宣言」であり、何を壊してはいけないかのリストになる。
2. **git 履歴を見る**: `git log --oneline -10` で直近の関心事（何が最近追加されたか）を知る。最近追加された機能は統合が甘いことが多く、バグの候補地になる。
3. **ファイル一覧で規模を測る**: `find`/`Glob` で全ファイルを列挙。小さいプロジェクトなら全ファイルを読む計画を立て、大きければ読む範囲を絞る根拠にする。
4. **README を全文読む**: これが検証すべき「約束リスト」になる。読みながら、コードと突合すべき具体的な主張（クラス名、設定値、手順）をメモする。

### 実例

- `git log` の「grid 関連プロパティ追加」という直近コミットが、後に見つかる「grid の gap 実装が displays.css と grid.css で二重定義され矛盾している」バグの発生源だった。**後から追加された機能と既存機構の縫い目**は最優先の捜索地点。

## 2. フェーズ 1: 仕様と実装の突合 — バグの探し方

### 2.1 ドキュメントの全主張を検証する

README・コメント・CLI の出力メッセージに書かれた仕様を 1 つずつコードと突き合わせる。

**実例（すべて実際に発見された不一致）:**
- README「`font:itaric`」→ 実装は `font:italic`（ドキュメントの typo）
- README「ブレークポイント 576/992/1200px」→ テンプレートの実値は 640/1024/1280px
- README「`col-span:1`〜`col-span:11`」→ 実装は 1〜12 + `full`
- README「Generic/Base は FlonCSS コアに含む」→ コア側は空ファイルで、実体は init 時にコピーされるテンプレート

### 2.2 参照と定義の突合（最も費用対効果が高い）

変数・トークン・シンボルの**参照**をすべて洗い出し、**定義**が到達可能な場所に存在するか機械的に確認する。CSS なら `var(--x)` と `--x:` の突合、JS なら import/export の突合。

**実例:**
- `gap:3xs` が参照する `--gap-3xs` が settings テンプレートに未定義（機能しないクラス）
- レガシー `lh:2xl` / `lh:xs` / `lh:2xs` の参照先変数が存在しない（v2 でも動いていなかった → 削除の根拠になった）

### 2.3 コピペ列の中の「1 行の逸脱」を探す

同じパターンの繰り返しブロック（ユーティリティ定義、enum 的な列挙）は、**パターンから外れた 1 行**を探しながら読む。人間はコピペ後の書き換えを忘れる。

**実例:**
- `.color\:red-light { color: var(--color-red); }` — 周囲はすべて `-light` サフィックス付き変数を参照しているのに、ここだけ書き換え漏れ。`color` / `bg-color` / `border-color` の 3 箇所で同じミス（コピペはミスも複製する）。

### 2.4 単位・型・境界値

言語の暗黙の型規則が壊れる箇所を探す。CSS なら「`calc()` 内の単位なし `0` は無効」「メディアクエリは `var()` を参照できない」など、**その言語で有名な落とし穴のチェックリスト**を頭に置いて読む。

**実例:**
- `.gap:none { --column-gap: 0 }`（単位なし）が `.cols` の `calc((100% + var(--column-gap)) / 12)` を無効化。直接 `column-gap: 0` として消費される分には合法なので、**消費側が複数あると片方だけ壊れる**。

### 2.5 二重定義・同名衝突

同じセレクタ / 同じ関数 / 同じ設定キーが複数ファイルで定義されていないか。あれば「どちらが勝つか」「勝った結果は意図か」を確認する。負けた側は死にコードであり、読者を誤解させる。

**実例:**
- `.grid` が displays.css（gap: 40px）と grid.css（column-gap: 0px）で二重定義。ソース順で grid.css が勝ち、displays.css 側は完全な死にコード。さらに `.inline-grid` は片方にしか存在せず、gap ユーティリティが効かない非対称が生まれていた。

### 2.6 「組み合わせ」で考える

単体では正しい機能同士の組み合わせを列挙して、壊れる組がないか考える。特に「レスポンシブ変形 × 非レスポンシブ機能」「オプション A × オプション B」のような直積。

**実例:**
- `flex@md`（media ファイル内、ソース順で後）× `gap:lg`（ベース、先）→ 同詳細度の後勝ちで gap が 0 に潰される。`flex` 単体・`gap:lg@md` 単体では正常なので、単体テスト的な読み方では見つからない。

## 3. フェーズ 2: 実行して確かめる — 検証環境の作り方

### 3.1 ユーザーの実環境を再現する

「リポジトリ内でビルドが通る」ことと「ユーザーの手順で動く」ことは別物。**README のクイックスタートを一字一句そのまま**実行する使い捨て環境を作る。

```
作業用 scratch ディレクトリで:
1. npm init -y
2. npm install <ローカルのリポジトリパス> + 必要な peer 依存
3. README の手順どおりに初期化・ビルド
4. 出力を検査
```

**実例:** この手順自体が「peerDependencies を optional 化すると README のクイックスタートが成立しなくなる」というバグの検出器になった（CI にも同じ手順を組み込んだ）。

### 3.2 出力（ビルド成果物）こそがグラウンドトゥルース

ソースではなく**コンパイル済み出力**を grep して検証する。ビルドパイプライン（プラグイン、ミニファイア）が意図を壊すことがあるため。

**実例:**
- `@layer` 導入時、出力サイズが 58KB → 257KB に膨張し `@layer` が消えていた。原因は postcss-preset-env の cascade-layers ポリフィルが `@layer` を `:not(#\#)` の詳細度ハック 8,000 箇所に変換していたこと。**「出力サイズ・形状の異常」は必ず根本原因まで追う**。想定 2 倍のサイズは「何かが 2 回入っている」か「何かが展開されている」。

### 3.3 動作の主張は実行環境で観測する

「この CSS 変数は後から上書きできるか」のような**動作に関する主張**は、仕様の推論で答えずに実行して観測する。ブラウザが絡むなら headless ブラウザで computed style を読む。

**実例:** 「min.css でもトークンを上書きできるか」というユーザーの核心的質問に対し、Playwright + Chromium で `getComputedStyle` を検証（margin-top / color / column-gap / レスポンシブ font-size の 4 項目）。「できます」という回答に実測の裏付けを持たせた。修正後の `flex@md gap:lg` = 64px も同様に実測で確認。

### 3.4 検証は「修正前に壊れていること」も確認する

可能なら、修正前の状態でバグが再現することも確かめる（またはビルド出力の該当箇所を確認する）。再現しないなら、それはバグではないか、理解が間違っている。

## 4. フェーズ 3: 修正の設計 — どう直すか

### 4.1 変更の 3 分類と扱い

| 分類 | 例 | 扱い |
|---|---|---|
| バグ修正 | 参照先変数の typo、無効な calc | 即修正。CHANGELOG の Fixed へ |
| 破壊的変更 | デフォルト値の変更、クラス削除 | メジャーバージョン + 移行ガイド必須。ユーザーの明示的な同意なしに勝手に行わない |
| ドキュメント | README の誤記 | 即修正 |

**重要:** 「既存の挙動が変」でも、ユーザーがそれに依存している可能性がある場合は**まずドキュメント化に留め、挙動変更は破壊的変更として提案する**。このセッションでも flex の暗黙 gap は、最初の修正コミットでは温存 + ドキュメント化し、ユーザーが「推奨の形に」と明示してから v3 破壊的変更として実施した。

### 4.2 正しい深さで直す（バンドエイドを貼らない）

症状のある場所に特例を足すのではなく、症状を生む**機構**を直す。判定基準: 「同じバグが別の場所・将来の追加で再発しうるか？」

**実例:**
- ソース順依存の gap バグ → 「import 順を調整する」のではなく、デフォルト値を `:where()`（詳細度 0）で宣言する方式に変更。**順序に依存した正しさを、順序非依存の仕組みに置き換える**。これにより flex / grid / cols すべてが、どんな読み込み順・ブレークポイントの組み合わせでも正しくなった。
- grid コンテナ変数の手動セレクタ列挙（10 個）→ 既存の mixin 機構に統合。ブレークポイント追加時の更新漏れという**将来のバグを構造的に不可能に**した。

### 4.3 「この diff 自体が証拠」ヒューリスティック

自分の変更が **N 箇所への同一編集**を要求したら、それは単一情報源への抽出が必要なサイン。

**実例:** `cascade-layers: false` の追加が 3 つの PostCSS 設定への同時編集を要求した。→ `postcss-features.js` に一元化し、3 箇所とも参照に変更。レイヤー順序リテラルも同様に `core/layers.css` へ。

### 4.4 プラットフォームの新機能で「規律」を「保証」に変える

規約・運用ルールで守られている不変条件（「import 順序を守ること」等）は、言語・プラットフォームのネイティブ機能で強制できないか常に検討する。

**実例:** ITCSS の「ユーティリティが常に勝つ」は import 順序という規律で守られていた → CSS の `@layer` で言語仕様レベルの保証に置き換え。ただし新機能の導入時は**ツールチェーンとの相互作用を必ず検証**する（ポリフィルの罠、リゾルバの exports 非対応など）。

### 4.5 パッケージングはランタイムと同格のバグ源

`exports` / `files` / `scripts`（`prepare` vs `prepublishOnly` の実行タイミング差）/ gitignore と配布物の関係 / CDN URL のバージョン固定。これらは「コードは正しいのに届かない」系の障害を生む。

**実例:**
- `dist/` は gitignore 済み + `prepublishOnly` でのみ生成 → git インストールや `npm pack` では exports が指すファイルが存在しない。`prepare` へ変更 + ビルドスクリプトを配布物に含めて解決。
- `exports` のエイリアス（`floncss/layers`）は、ユーザーのビルドチェーンのリゾルバ（enhanced-resolve 4.x）が exports マップ非対応で解決不能だった → 実パス参照に変更。**「エコシステムの最小公倍数」で疎通確認する**。

## 5. フェーズ 4: 多視点セルフレビュー — 自分の変更を疑う

変更が一段落したら、自分の diff に対して**独立した複数の観点**でレビューをかける。並列サブエージェントが使えるなら並列に、使えないなら観点ごとに順番に通す。1 つの視点で通読するより、**視点を変えた複数回の走査**のほうが検出率が高い。

### 推奨する観点セット

1. **行単位スキャン**: diff の全 hunk を 1 行ずつ。「どんな入力・状態・タイミング・環境ならこの行は間違いか」
2. **削除挙動の監査（リファクタで最高利得）**: 削除・置換した各行について「その行が守っていた不変条件は何か」を言語化し、新コードでどこに再確立されたかを探す。見つからなければバグ候補。
3. **クロスファイル追跡**: 変更したものの「消費者」を追う。関数なら呼び出し元、exports なら import 側、CI の grep なら実際の出力、設定ならそれを読むツール。
4. **再利用**: 新コードが既存機構を再発明していないか
5. **簡素化**: 死にコード、導出可能な状態、コピペ変奏
6. **効率**: 無駄な二重処理、出力の肥大化
7. **実装深度**: 特例を積んでいないか、より深い機構で解けないか

### 検出→検証→対処のパイプライン

- 各観点の指摘は「候補」として扱い、**実証（ビルド・実行・出力確認）してから**修正する
- 複数の独立した観点が同じ箇所を指摘したら、それは最優先(このセッションでは 3 観点が「設定の 3 重複」を独立に指摘した)
- 対処しないと決めた指摘は**理由付きでロードマップに記録**する（黙殺しない）

**実例:** このパイプラインが、自分では見落としていた「プリビルドのレイヤー宣言に objects/components が無く、ドキュメントの案内どおりにすると保証が反転する」という重大バグを検出した。**自分が書いたドキュメントの約束も検証対象**。

## 6. フェーズ 5: ドキュメントと引き継ぎ

### 成果物は 3 層で書き分ける

| 成果物 | 読者 | 内容 |
|---|---|---|
| CHANGELOG | 利用者 | 何が変わったか + **移行方法**。破壊的変更は「移行方法」を必ず併記 |
| 引き継ぎ資料（HANDOVER） | 次の保守者 | **なぜ**そうしたか、非自明な制約、やらないと決めたことと理由、優先度付きロードマップ |
| コード内コメント | 未来の編集者 | その場で守るべき制約のみ（例:「`--column-gap` に単位なし 0 を入れてはいけない、calc が壊れる」） |

### 「なぜ」を制約の発生地点に書く

非自明な制約（`0px` の単位、`cascade-layers: false` 必須、`:where()` を使う理由）は、**次の人がそれを変更しようとしたときに目に入る場所**に理由を書く。コミットメッセージにも「原因 → 修正 → 検証方法」の物語を残す。

## 7. ワークフロー運用のコツ

- **並列化**: 依存関係のない読み取り・調査・サブエージェントは同時に走らせる。レビューの 8 観点は全部並列でよい。
- **使い捨て環境**: 実験・再現・検証はすべて scratch ディレクトリで。プロジェクトを汚さない。
- **マイルストーンごとにコミット & プッシュ**: 「バグ修正」「破壊的変更」「レビュー反映」のような意味単位で分ける。レビュー結果の修正は独立コミットにすると、何がレビュー由来か履歴で追える。
- **CI を最初のマイルストーンで植える**: 「実ユーザー手順の再現 + 出力検証」の CI を早期に作ると、以後の全変更の安全網になる。このセッションでも自分の後続変更が CI 相当のチェックで何度も検証された。
- **CI のアサーションはツールの直列化に依存させない**: ミニファイアの出力バイト列を丸ごと grep すると、ツールのバージョンアップで偽陽性が出る。「宣言が存在する」「禁止パターンが存在しない」レベルの不変条件でアサートする。
- **ユーザーへの報告は「結論 → 根拠 → 詳細」**: 質問には実測値で答える。「できます（検証済み: 条件 X でこう観測した）。ただし例外は Y」の形。
- **確認すべきものと進めてよいものの区別**: 依頼の範囲内で可逆な作業は進める。破壊的変更・スコープ変更はユーザーの明示を待つ。「その他推奨の改善を行って」のような包括的指示を受けたら、それまでに自分が提示した推奨リストが承認範囲になる。

## 8. 着眼点チェックリスト（携帯版）

レビュー時に頭に置く質問のリスト。

**バグ探索**
- [ ] README / ドキュメントの全主張はコードと一致するか
- [ ] すべての参照（変数・import・設定キー）に到達可能な定義があるか
- [ ] コピペ列に「パターンから外れた 1 行」はないか
- [ ] 単位・型の境界（calc 内の 0、文字列エスケープ、パス区切り文字）は正しいか
- [ ] 同名の二重定義はないか。あるならどちらが勝ち、それは意図か
- [ ] 機能 A × 機能 B の組み合わせ（特にレスポンシブ × 非レスポンシブ）で壊れる組はないか
- [ ] ソース順・詳細度・読み込み順に依存した正しさはないか
- [ ] ツールチェーンのデフォルト動作（ポリフィル、自動変換、自動インストール）が意図を壊していないか
- [ ] パッケージング（exports / files / scripts のタイミング / 配布物と gitignore）は全インストール経路で成立するか
- [ ] Windows 等、別プラットフォームでパスや文字列が壊れないか

**リファクタ品質**
- [ ] 同じ知識（設定・リスト・定数）が 2 箇所以上に手動複製されていないか
- [ ] 規約で守っている不変条件を、言語機能で保証に変えられないか
- [ ] 手動列挙は既存の生成機構（mixin / ループ / スキーマ）に統合できないか
- [ ] 削除した各行の不変条件は、新コードのどこで再確立されているか
- [ ] デフォルト値の変更はユーザーの既存依存を壊さないか（壊すならメジャー + 移行ガイド）

**検証**
- [ ] ユーザーの実手順をゼロから再現したか
- [ ] ビルド出力（ソースではなく）を検査したか
- [ ] 動作の主張を実行環境（ブラウザ等）で観測したか
- [ ] 出力サイズ・形状の異常を根本原因まで追ったか
- [ ] 自分のドキュメントに書いた約束も検証したか

## 9. アンチパターン（やってはいけないこと）

- **読んだだけで「正しい」と報告する** — 実行していない検証は検証ではない
- **ビルドが通った = 動く、と判断する** — 出力の中身と実行時挙動まで見る
- **異常（サイズ膨張、警告、消えた構文）を「まあ動いてるから」で流す** — 異常は必ず説明がつくまで追う
- **既存の変な挙動を黙って「正しく」直す** — それに依存するユーザーを黙って壊すことになる。分類してから直す
- **レビュー指摘を検証せずに全部直す / 検証せずに全部却下する** — 候補→実証→対処のパイプラインを守る
- **対応しない指摘を黙って捨てる** — 理由付きでロードマップへ
- **同じ編集を N 箇所に繰り返して満足する** — それは単一情報源化のサイン
- **ドキュメントを最後にまとめて書こうとして書き忘れる** — 制約を発見したその場で、発生地点に書く

## 付録: このセッションの実際の流れ（タイムライン）

1. **全体把握**（package.json → git log → ファイル一覧 → README 全文 → 全ソース読了）
2. **バグ発見**（仕様突合 + 参照定義突合 + コピペ逸脱スキャン）→ 実環境再現ビルドで確認 → 修正 → 出力で検証 → コミット
3. **ユーザー承認済みの推奨改善**（レガシー削除、ドキュメント整合、CI 新設）→ コミット
4. **アーキテクチャ更新**（@layer、gap オプトイン化、プリビルド同梱）→ ポリフィル異常を出力サイズで検出・解決 → コミット → PR 作成
5. **多視点セルフレビュー**（8 観点並列）+ ユーザーの核心質問（変数上書き可否）へのブラウザ実測回答 → 検出バグ修正（:where() 化、レイヤー宣言一元化、パッケージング修正）→ 単一情報源化 → リリースノート・引き継ぎ資料 → コミット
6. 各マイルストーンでプッシュし、PR に履歴として蓄積

各フェーズの検証は「scratch 環境での実手順再現 + ビルド出力 grep + 必要に応じて headless ブラウザでの computed style 観測」の三段構えで統一した。
